# Product Specification: Canopy - The Flight Deck for Agentic Coding

## 1. Executive Summary

Canopy is an open-source, AI-native Terminal User Interface (TUI) that reimagines how developers navigate and understand codebases in the age of agentic coding. Rather than presenting the traditional file-and-folder hierarchy that has dominated source code editors for decades, Canopy renders codebases as C4-style architectural views—organizing code into systems, containers, and components with human-readable summaries of responsibilities, dependencies, and relationships.

Built in Rust with Ratatui, Canopy requires zero configuration: point it at any repository and immediately see the architectural shape of the codebase. AI generates the semantic layer first; developers refine and augment as needed. Every structural edit is captured in a JSONL log with full provenance, enabling future agent-driven refactoring and organizational learning.

**Value Proposition:** Canopy elevates developers from line-level code navigation to system-level architectural thinking, aligning the tool with how modern agentic coding actually works—defining requirements, designing architecture, and orchestrating AI agents rather than typing code character by character.

## 2. Problem Statement

### 2.1 Current Pain Points

| Pain Point | Description | Impact |
|------------|-------------|--------|
| **Wrong level of abstraction** | Existing editors (vim, emacs, VSCode) present code as files, directories, and lines of syntax. Developers doing agentic coding think in terms of components, responsibilities, and system relationships. | Constant cognitive translation between how they think and how tools present information |
| **Context-switching overhead** | Developers must mentally switch between architectural reasoning (what components exist, how they interact) and low-level navigation (which file, which line). | Mental fatigue, lost productivity, increased error rates |
| **No unified architectural view** | Understanding a codebase requires piecing together information from file explorers, documentation (often outdated), and code reading. | Hours spent on codebase comprehension; tribal knowledge bottlenecks |
| **Bolted-on AI features** | Current tools add AI as a feature to legacy paradigms rather than rethinking the paradigm for AI-native workflows. | Suboptimal workflows; AI capabilities underutilized |
| **Zero-to-productive friction** | Joining a new project requires significant ramp-up time to understand architecture. | Slower onboarding; reduced team velocity |

### 2.2 Impact of the Problem

**For Individual Developers:**
- 30-50% of development time spent on code comprehension and navigation (industry research)
- Cognitive load from abstraction mismatch reduces deep work capacity
- Frustration with tools that don't match modern workflows

**For Teams:**
- Knowledge silos form around developers who understand system architecture
- Onboarding new team members takes weeks instead of hours
- Architectural decisions are poorly documented and easily violated

**For Organizations:**
- Technical debt accumulates as developers lack visibility into system relationships
- Agentic coding investments underperform due to workflow friction
- Competitive disadvantage against teams with better tooling

### 2.3 Why Now?

1. **Agentic coding has reached critical mass.** Tools like GitHub Copilot, Cursor, Claude Code, and autonomous coding agents have fundamentally changed developer workflows. The transition from "writing code" to "orchestrating agents" is accelerating.

2. **LLM capabilities have matured.** Modern LLMs can reliably analyze code, infer architectural relationships, and generate human-readable summaries—capabilities that were unreliable or impossible two years ago.

3. **Developer expectations are shifting.** A new generation of developers expects AI-native tools. The window for establishing the paradigm for agentic-era development tools is open now.

4. **TUI renaissance.** Terminal-based tools are experiencing renewed interest (Helix, Zellij, Lazygit) as developers seek keyboard-driven, distraction-free environments. Modern TUI frameworks like Ratatui make building sophisticated terminal applications practical.

5. **Open-source opportunity.** No open-source project currently occupies this space, creating an opportunity for community-driven innovation and adoption.

## 4. Product Overview

### 4.1 Vision Statement

**In 3 years:** Canopy is the standard way developers understand and navigate codebases. The question "How does this codebase work?" is answered in seconds, not hours. Architectural documentation is always accurate because it's continuously generated and refined. AI agents have rich context because Canopy provides the semantic layer they need.

**In 5 years:** The distinction between "code" and "architecture" dissolves. Developers work fluidly at whatever level of abstraction suits their task. Canopy's edit log has become a rich history of architectural evolution, enabling AI-driven refactoring suggestions and organizational learning about how systems evolve.

### 4.2 Core Value Proposition

| For | Who | Canopy Is | That | Unlike |
|-----|-----|-----------|------|--------|
| Developers embracing agentic coding | Need to understand and navigate complex codebases | An AI-native architectural browser | Presents code as systems, containers, and components with human-readable summaries | Traditional editors that show files and syntax |

**The Canopy Promise:**
> "Point Canopy at any repository. In under a minute, understand its architecture."

### 4.3 Key Differentiators

| Differentiator | Description | Why It Matters |
|----------------|-------------|----------------|
| **Architecture-First, Not File-First** | C4-style hierarchy (System → Container → Component) is the primary navigation model | Matches how developers think about large codebases |
| **AI-Generated Semantic Layer** | Responsibilities, dependencies, and relationships in plain language | No more reading code to understand what it does |
| **Zero Configuration** | Point at any repo and go | Removes adoption friction; works with any codebase |
| **Provenance-Tracked Edits** | Every human refinement logged with what/why/when | Enables learning and future automation |
| **TUI-Native** | Terminal-based, keyboard-driven, distraction-free | Fits developer workflows; no context-switch to GUI |
| **Language-Agnostic** | LLM-powered understanding works across languages | One tool for polyglot codebases |
| **Open Source** | Community-driven development | Trust, transparency, extensibility |

## 5. Features & Requirements

### 5.1 MVP Features (Must Have)

#### F1: Zero-Config Repository Loading

**Description:** User can point Canopy at any Git repository and begin exploring immediately.

**Requirements:**
| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F1.1 | Accept repository path as CLI argument | `canopy /path/to/repo` opens Canopy with that repository |
| F1.2 | Auto-detect repository root | Finds `.git` directory and establishes project boundaries |
| F1.3 | Initial scan completes in <60 seconds | For repositories up to 100K LOC, initial C4 view appears in under 1 minute |
| F1.4 | Progressive loading | UI is interactive while deeper analysis continues in background |
| F1.5 | BYOK (Bring Your Own Key) | Reads API keys from environment variables (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, etc.) |

#### F2: C4-Style Hierarchical View

**Description:** Codebase presented as a navigable hierarchy following C4 model principles.

**Requirements:**
| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F2.1 | System level view | Top-level view shows major systems/domains in the codebase |
| F2.2 | Container level view | Drilling into a system shows containers (services, applications, data stores) |
| F2.3 | Component level view | Drilling into a container shows components (modules, classes, significant functions) |
| F2.4 | Code level access | Drilling into a component shows actual source code |
| F2.5 | Breadcrumb navigation | Current location in hierarchy always visible |
| F2.6 | Collapse/expand nodes | Ability to expand/collapse hierarchy nodes |

#### F3: AI-Generated Semantic Summaries

**Description:** Each node in the hierarchy has human-readable summaries of its purpose and relationships.

**Requirements:**
| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F3.1 | Responsibility summary | Each component shows 1-3 sentence description of what it does |
| F3.2 | Dependency listing | Shows what this component depends on (uses) |
| F3.3 | Dependent listing | Shows what depends on this component (used by) |
| F3.4 | Confidence indicator | Visual indicator of AI confidence in the inference |
| F3.5 | Last analyzed timestamp | Shows when the summary was last generated/verified |

#### F4: Vim-Style Keyboard Navigation

**Description:** Familiar keyboard-driven interface for terminal-native developers.

**Requirements:**
| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F4.1 | HJKL navigation | Standard vim directional movement |
| F4.2 | Enter to drill down | Enter key descends into selected node |
| F4.3 | Backspace/Escape to go up | Backspace or Escape ascends in hierarchy |
| F4.4 | `/` to search | Search within current view |
| F4.5 | `?` for help | Shows keyboard shortcut reference |
| F4.6 | `q` to quit | Standard quit behavior |
| F4.7 | `g` + motion | Go-to shortcuts (gg for top, G for bottom) |

#### F5: Natural Language Query Interface

**Description:** Text input for asking questions about the codebase.

**Requirements:**
| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F5.1 | Query input activation | `:` or dedicated key opens query input |
| F5.2 | @-mention components | `@ComponentName` syntax to reference specific components |
| F5.3 | Query response display | Responses shown in dedicated pane |
| F5.4 | Navigate to mentioned items | Can jump to components mentioned in response |
| F5.5 | Query history | Up arrow recalls previous queries |

#### F6: JSONL Edit Log

**Description:** All structural edits captured with provenance for future use.

**Requirements:**
| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F6.1 | Log location | Edit log stored at `.canopy/edit_log.jsonl` in repository |
| F6.2 | Edit capture | Each edit records: timestamp, author, component path, before/after, reason |
| F6.3 | Append-only | Log is append-only; no edits are deleted |
| F6.4 | View edit history | UI command to view edit history for current component |
| F6.5 | Export capability | Can export log to standard formats |

#### F7: Summary Editing

**Description:** Users can correct or enhance AI-generated summaries.

**Requirements:**
| ID | Requirement | Acceptance Criteria |
|----|-------------|---------------------|
| F7.1 | Edit activation | `e` key on selected summary enters edit mode |
| F7.2 | Inline editing | Edit happens in-place in the TUI |
| F7.3 | Reason prompt | After edit, prompts for reason (optional but encouraged) |
| F7.4 | Provenance marking | Edited summaries visually distinguished from AI-generated |
| F7.5 | Regenerate option | `r` key regenerates AI summary (with confirmation if human-edited) |

### 6.4 Security & Privacy

#### 6.4.1 Data Handling

| Data Type | Handling | Storage |
|-----------|----------|---------|
| Source code | Sent to LLM for analysis | Not stored externally |
| API keys | Read from environment | Never logged or stored |
| Summaries | Cached locally | `.canopy/` directory |
| Edit log | Stored locally | `.canopy/edit_log.jsonl` |
| Query history | Stored locally | `.canopy/query_history.jsonl` |

#### 6.4.2 Security Requirements

| Requirement | Implementation |
|-------------|----------------|
| No telemetry without consent | Opt-in only; disabled by default |
| Secure API key handling | Environment variables only; no config file storage |
| Local-only by default | All persistent data in `.canopy/` (gitignore recommended) |
| Audit trail | Edit log provides accountability |
| Code never persisted externally | Only sent to LLM providers for inference |

#### 6.4.3 Privacy Considerations

- **Enterprise Use:** Document that code is sent to LLM providers; enterprises may need to use private deployments
- **Sensitive Detection:** Warn before sending files that might contain secrets (future feature)
- **Local Model Option:** Planned for privacy-sensitive environments

## 9. FAQ

### For Engineers

**Q: How does Canopy infer the C4 architecture from code?**
A: Canopy uses a multi-pass LLM analysis:
1. **Pass 1:** File/directory structure analysis to identify major boundaries
2. **Pass 2:** Import/dependency graph construction
3. **Pass 3:** Semantic analysis of significant files (entry points, configs, key modules)
4. **Pass 4:** LLM synthesis into C4 model with confidence scores

The result is stored in `.canopy/c4_model.json` and incrementally updated.

**Q: What happens when the LLM gets it wrong?**
A: Users can edit any summary or structural element. Edits are logged with provenance and take precedence over AI inference. The edit log can be used to improve future inference (fine-tuning data).

**Q: How do we handle very large codebases?**
A: Progressive loading strategy:
- Initial view shows high-level structure (usually inferrable from directories)
- Deeper analysis happens on-demand as user navigates
- Aggressive caching means subsequent loads are fast
- Background processing continues while user explores

**Q: What's the architecture for supporting multiple LLM providers?**
A: A `LlmProvider` trait defines the interface:
```rust
trait LlmProvider {
    async fn complete(&self, prompt: Prompt) -> Result<Completion>;
    async fn stream_complete(&self, prompt: Prompt) -> Result<Stream<CompletionChunk>>;
    fn model_info(&self) -> ModelInfo;
}
```
Each provider (OpenAI, Anthropic, etc.) implements this trait. Provider selection is based on environment variables and optional config.

**Q: How do we test C4 inference quality?**
A: Multi-pronged approach:
1. **Golden set:** Curated repositories with human-verified C4 models
2. **Property tests:** Invariants (every file maps to exactly one component, no orphans, etc.)
3. **User feedback loop:** Thumbs up/down on inferences feeds back to evaluation
4. **Dogfooding:** Canopy's own codebase is a primary test case

### For Product Managers

**Q: Why TUI instead of GUI?**
A: Strategic differentiation:
1. Developer audience is terminal-native; TUI fits workflow
2. Keyboard-driven is faster than mouse-driven for navigation
3. Lighter weight, faster to start, less resource usage
4. Unique positioning in market (no one else doing this)
5. Easier to develop/maintain than cross-platform GUI

We may add IDE integration later, but TUI is the core product.

**Q: Why open source?**
A: Open source is strategic for this product:
1. **Trust:** Developers are skeptical of AI tools; transparency builds trust
2. **Adoption:** Lower barrier to try; essential for developer tools
3. **Community:** Harness collective knowledge for language support, prompts, etc.
4. **Hiring:** Attracts contributors who become advocates
5. **Market timing:** Need to move fast; open source accelerates this

Monetization (if needed) can come through enterprise features, support, or hosting—not the core product.

**Q: How do we handle the "zero config" promise for edge cases?**
A: Zero config means "works out of box with reasonable defaults." Edge cases:
- **No API key:** Clear error message with instructions
- **Unusual project structure:** Falls back to file-based view with prompt to refine
- **Rate limited:** Graceful degradation to cached data
- **Offline:** Works with cached data; syncs when online

The experience should never feel broken, just potentially limited.

**Q: What's the competitive moat?**
A: Several layers:
1. **First-mover:** Defining the category
2. **Edit log data:** Accumulating human refinements improves over time
3. **Community:** Active users, contributors, advocates
4. **Prompt engineering:** Tuned prompts for different languages/frameworks
5. **UX innovation:** Navigation patterns we'll pioneer

### For Users

**Q: Will Canopy work with my private/enterprise codebase?**
A: Yes, with caveats:
- Code is sent to your configured LLM provider (OpenAI, Anthropic, etc.)
- Check your organization's policies on sending code to these APIs
- Local model support (Phase 3) will enable fully offline use
- All cached data stays local in `.canopy/` directory

**Q: How much will this cost me in API fees?**
A: Rough estimates (varies by provider and model):
- Initial scan of 100K LOC repo: $0.50-2.00
- Typical daily use (navigation, queries): $0.10-0.50
- Heavy query use: Could be higher

We're implementing aggressive caching and batching to minimize costs. Future local model support will eliminate ongoing API costs.

**Q: Can I use Canopy alongside my existing editor?**
A: Absolutely—that's the expected use case. Canopy complements your editor:
- Use Canopy to understand architecture and navigate to the right place
- Use your editor (vim, VSCode, etc.) to write/edit code
- Switch fluidly between them

### 10.1 Glossary

| Term | Definition |
|------|------------|
| **Agentic Coding** | Development workflow where AI agents generate significant portions of code, with humans guiding through requirements and review |
| **C4 Model** | A hierarchical software architecture model with four levels: Context, Containers, Components, and Code (created by Simon Brown) |
| **System** | (C4) Top-level software system; in Canopy, typically maps to a repository or major bounded context |
| **Container** | (C4) Deployable/runnable unit; in Canopy, typically maps to services, applications, or major packages |
| **Component** | (C4) Grouping of related functionality; in Canopy, typically maps to modules, classes, or significant files |
| **TUI** | Terminal User Interface; text-based interface running in a terminal emulator |
| **BYOK** | Bring Your Own Key; users provide their own API keys for LLM services |
| **Semantic Layer** | The human-readable summaries, relationships, and metadata that Canopy generates about code |
| **Provenance** | Record of origin and changes; in Canopy, tracking whether content is AI-generated or human-edited |
| **Edit Log** | Append-only JSONL file recording all human edits to the semantic layer |
| **Inference** | The process of deriving architectural structure from code analysis |
| **Golden Set** | Curated test cases with known-correct outputs for quality validation |
